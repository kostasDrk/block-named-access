Task 1.b

When opening this page with a regular Chromium browser, the following error message should be logged in the console:
"Unrecognized Content-Security-Policy directive 'block-named-access'."
Instead, the modified Chromium recognizes the directive and the message does not appear.

Task 1.c

This page contains two named elements to demonstrate the directive's enforcement.

  • A dummy link (<a id='myLink'>)
  • A dummy image: (<img name='myImg'/>)
In a regular browser, each of them clobbers the window.myLink and document.myImg JavaScript properties, respectively. When accessing any of them the corresponding named element is returned, which is the root cause of DOM clobbering vulnerabilities.
In the modified Chromium, however, the clobbering is prevented, thus eliminating the vulnerability's root cause. Specifically, the properties return undefined when accessed, and a detailed security error message is logged in the console.

Task 1.d

Demonstrating `block-named-access` in a Content-Security-Policy-Report-Only deployment (no enforcement) is not possible due to:

  • GitHub Pages not allowing to set custom headers.
  • Content-Security-Policy-Report-Only cannot be set from a <meta> tag (as is the case for a regular CSP, i.e., this page).
However, it can be trivially replicated by deploying this page in a local HTTP server, removing the <meta> element with the regular CSP deployment from its <head>, and setting the response header:
Content-Security-Policy-Report-Only: block-named-access
In a report-only deployment, the directive will not prevent the properties from being clobbered, but will log the warning messages and raise any violation events (see Task 1.e).

Task 1.e

Whenever a violation is detected by `block-named-access` it is reported both as a securitypolicyviolation JavaScript event (see console) and is sent as a violation report in the corresponding `report-uri` or `report-to` endpoints.
